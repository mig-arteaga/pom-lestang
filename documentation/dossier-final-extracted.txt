Présentation du dossier
Le dossier professionnel (DP) constitue un élément du système de validation du titre professionnel.
Ce titre est délivré par le Ministère chargé de l’emploi.
Le DP appartient au candidat. Il le conserve, l’actualise durant son parcours et le présente
obligatoirement à chaque session d’examen.
Pour rédiger le DP, le candidat peut être aidé par un formateur ou par un accompagnateur VAE.
Il est consulté par le jury au moment de la session d’examen.
Pour prendre sa décision, le jury dispose :
1. des résultats de la mise en situation professionnelle complétés, éventuellement, du questionnaire
professionnel ou de l’entretien professionnel ou de l’entretien technique ou du questionnement à partir de
productions.
2. 3. 4. du Dossier Professionnel (DP) dans lequel le candidat a consigné les preuves de sa pratique professionnelle.
des résultats des évaluations passées en cours de formation lorsque le candidat évalué est issu d’un parcours
de formation
de l’entretien final (dans le cadre de la session titre).
[Arrêté du 22 décembre 2015, relatif aux conditions de délivrance des titres professionnels
du ministère chargé de l’Emploi]
Ce dossier comporte :
▶ pour chaque activité-type du titre visé, un à trois exemples de pratique professionnelle ;
▶ un tableau à renseigner si le candidat souhaite porter à la connaissance du jury la détention d’un titre, d’un
diplôme, d’un certificat de qualification professionnelle (CQP) ou des attestations de formation ;
▶ une déclaration sur l’honneur à compléter et à signer ;
▶ des documents illustrant la pratique professionnelle du candidat (facultatif)
▶ des annexes, si nécessaire.
Pour compléter ce dossier, le candidat dispose d’un site web en accès libre sur le site.

Recherche et préparation des éléments graphiques :
• Recherche d’une planche de personnages en 2D sur internet pour créer le sprite (succession

• Rognage des parties nécessaires pour obtenir 25 images consécutives représentant le
mouvement de Yoshi.
• Utilisation de Figma pour créer les éléments de décor tels que les arbres, les herbes, le ciel et les

Création du fichier HTML :

différentes parallaxes (Cf. Annexes, Activité Type 1, Exemple 2, Pic. 15a).
Mise en forme avec CSS :
• Réinitialisation des marges avec un reset CSS.
• Positionnement de Yoshi en absolu pour un placement précis sans être affecté par les autres
éléments de la page.
• Utilisation de la propriété animation sur les classes .yoshi-left et .yoshi-right avec la
fonction steps(25) pour créer un effet de marche à la vitesse de 3 secondes.
• Ajout de la propriété transform: scaleX(-1) pour inverser l’animation vers la gauche.
• Positionnement des éléments de décor pour créer un effet de répétition infinie.
• Utilisation de keyframes pour créer un effet de mouvement plus ou moins lent, simulant le
défilement du paysage.

• Affichage d’une modal au chargement de la fenêtre avec une description de l’utilisation de

Interactions utilisateur :

• keydown (marche) : Ajout de la classe .yoshi-left ou .yoshi-right pour changer la

• keyup (arrêt) : Retrait des classes .yoshi-left et .yoshi-right pour arrêter les animations

1. Décrivez les tâches ou opérations que vous avez effectuées, et dans quelles conditions :
Avant de pouvoir coder la partie back-end, je réalise le MCD (Cf. Annexe, Activité Type 2, Exemple 1,
Pic.18) ainsi que les diagrammes de cas d’utilisation (Cf. Annexe, Activité Type 2, Exemple 1, Pic.19) et
le diagramme de séquence pour le login (Cf. Annexe, Activité Type 2, Exemple 1, Pic.20) à l'aide du
logiciel FigJam (Figma).
Je peux maintenant me concentrer sur la partie back-end de l'application Zoo Arcadia, développée avec
le framework Laravel pour gérer les fonctionnalités administratives et les données du zoo de manière
sécurisée et performante.
En utilisant la commande php artisan make:migration create_habitats_table, je crée la table des
habitats et la complète dans la migration (Cf. Annexe, Activité Type 2, Exemple 1, Pic.21). Cela me
permet ensuite de créer des seeders, qui me fourniront des entrées dans la base de données en local,
évitant ainsi de réécrire les données à chaque modification ou suppression lors des tests de mes
fonctionnalités.
J’ai porté une attention particulière à la sécurité des accès grâce à une gestion précise des rôles et des
permissions avec la façade Gate – Policy (Cf. Annexe, Activité Type 2, Exemple 1, Pic.22).
Concernant les fonctionnalités, le back-end permet une gestion complète des utilisateurs. Un système
d’authentification sécurisé a été mis en place pour limiter l’accès aux seuls administrateurs, vétérinaires
et employés, empêchant les visiteurs de créer des comptes (Cf. Annexe, Activité Type 2, Exemple 1,
Pic.23). Chaque rôle dispose de permissions spécifiques : l’administrateur gère les comptes, habitats,
services et animaux ; les vétérinaires saisissent des rapports médicaux sur les animaux et ajoutent des
commentaires sur les habitats ; les employés valident les avis des visiteurs, modifient les services
proposés et répondent aux messages reçus via le formulaire de contact.
La gestion des données du zoo est un élément essentiel. Par exemple, pour les habitats des animaux, il
est possible d’ajouter, consulter, modifier ou supprimer des informations grâce à un système appelé
CRUD (Create, Read, Update, Delete).
• Créer un habitat (Create) : Cette action permet d’ajouter un nouvel habitat. Les informations
sont saisies via un formulaire validé (HabitatsFormRequest) avant d’être enregistrées dans la
base de données. (Cf. Annexe, Activité Type 2, Exemple 1, Pic.24)
• Consulter les habitats (Read) : Il existe plusieurs façons de lire les informations des habitats :
o index : Affiche la liste complète des habitats. (Cf. Annexe, Activité Type 2, Exemple 1,
Pic.25)
o show : Permet d’afficher les détails d’un habitat précis en fonction de son nom. Si

La sécurité a été une priorité tout au long du développement. Les mots de passe sont hashés avec
Bcrypt automatiquement par Laravel et les permissions sont définies à l’aide des Policies et Gates (Cf.
Annexe, Activité Type 2, Exemple 1, Pic.31, 32 et 33) pour garantir que chaque utilisateur n’accède
qu’aux fonctionnalités qui lui sont autorisées. Les formulaires incluent des tokens Cross-Site-Request-
Forgery (les jetons @csrf) pour éviter de contourner les droits administrateurs. Également, les
identifiants de connexion à la base de données sont protégés dans un fichier .env .
D’un point de vue technique, j’ai choisi Laravel pour sa simplicité et sa robustesse. L’utilisation
d’Eloquent ORM (Object Relationship Manager) facilite les interactions avec la base de données MySQL,
utilisée pour les données structurées comme les utilisateurs ou les habitats. (Cf. Annexe, Activité Type
2, Exemple 1, Pic.34, 35 et 36) pour visualiser ce que donneraient les requêtes en MariaDB).
MongoDB, en revanche, a été adopté pour stocker les statistiques de consultation des animaux. (Cf.
Annexe, Activité Type 2, Exemple 1, Pic.37 : Installation MongoDB pour Laravel, et Pic 38, 39a et 39b :
Controller, migration et Model)
Le stockage des fichiers, comme les images des animaux et habitats, est géré via le système intégré de
Laravel (Storage) pour une organisation claire et sécurisée.
Enfin, le projet a été développé dans un environnement configuré avec l’IDE PHPStorm, ce qui a permis
un flux de travail fluide et efficace. L’application a été déployée sur un VPS Debian via Docker, (Cf.
Annexe, Activité Type 2, Exemple 1, Pic.40 à 43 : Dockerfile, docker-compose, mongo-init et Makefile)
bien que quelques défis aient été rencontrés lors de la configuration, notamment avec Nginx, les
domaines SSL et le protocole sécurisé https.
Pour les tests, des scénarios manuels ont permis de simuler les actions des différents utilisateurs.

1. Décrivez les tâches ou opérations que vous avez effectuées, et dans quelles conditions :
L’application QuizApp a été réalisée dans le cadre de ma formation DWWM.
Tout d’abord, j’ai initialisé mon repository sur GitHub, puis j’ai cloné mon projet sur PHPStorm afin de
commencer à structurer mon application. (Cf. Annexe, Activité Type 2, Exemple 2. Pic.47 – Structure du
projet)
Puisque j’ai travaillé en PHP vanilla, j’ai organisé mon projet avec :
• un répertoire classes/ contenant mes classes PHP (Autoloader, Database, Question et Quiz),
• un répertoire public/ destiné aux fichiers CSS et JavaScript.
Structure du code :
J’ai créé un Autoloader avec la méthode register() qui enregistre autoload().
Ainsi, dès qu’une classe est instanciée, PHP appelle automatiquement autoload(), ce qui permet de
récupérer les classes sans avoir à les inclure manuellement à chaque fois avec require_once.
La classe Database gère la connexion à la base de données et assure qu’elle n’est instanciée qu’une
seule fois, ce qui évite d’écrire new PDO() à plusieurs endroits dans le code.
La classe Question permet de récupérer les questions et leurs réponses associées depuis la base de
données, en utilisant la connexion fournie par la classe Database.
Enfin, la classe Quiz vérifie les réponses d’un utilisateur et calcule son score.
Intégration de la base de données :
Pour intégrer ma base de données à mon application, j’ai choisi AlwaysData. (Cf. Annexe, Activité Type
2, Exemple 2. Pic.48 – Connexion à la base de données MariaDB via AlwaysData sur PHPStorm)
Une fois ma base de données prête, je me place dessus :
i-jurain_quiz
Puis, je fais un clic droit sur ma base et j’ouvre une nouvelle console :
New -> Query Console
Je peux alors créer mes tables (Cf. Annexe, Activité Type 2, Exemple 2. Pic.49) et exécuter mes requêtes
via la console SQL de PHPStorm. (Cf. Annexe, Activité Type 2, Exemple 2. Pic.50)
